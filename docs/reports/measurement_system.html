给上下文管理造一把尺子:评测体系从设计到落地的迭代

📅 2026-06-11 ~ 06-15 🏷 needle-in-conversation eval 📊 2 档数据集 · 双轴指标 · debugger 可视化

在动手改上下文管理之前,我们先花了几天造一把尺子。这篇讲的不是某个策略,而是怎么量:两条评测轴怎么定、token 和准确度的指标怎么设计、needle 数据集怎么构造、怎么可视化,以及落地时踩的坑。一句话动机——你没法改进一个你量不了的东西。

1. 为什么先造尺子

原本的上下文管理是"把整个 session 历史暴力拼接发给 LLM"。我们想升级成分层管理(滑动窗口+摘要 → RAG → 跨 session)。但只要一问"新策略到底省了多少 token、答案有没有变差",就会发现没有任何客观依据——全靠感觉。于是定下原则:测量体系先于任何策略改动上线,先把暴力拼接(concat)这个基线量化清楚,之后所有策略和它对比。concat 永远是满分上限(它带了全部上下文),也是永远可用的回退。

2. 两条轴,必须一起读

评测沿两条轴:效率(token 成本)和准确度(信息找回能力 / 幻觉程度)。关键认知是这两条必须一起报告:

  • 单看效率没有意义——把 context 全删光效率最高;
  • 单看准确度也没有意义——全量 concat 准确度上限最高。

每个策略是这个二维平面上的一个点,好策略 = 准确度不降的前提下省 token。还有一条纪律:效率数字只在固定数据集上可比(不同问题天然体积不同),所以所有策略跑同一套脚本,同一次运行同时产出效率和准确度两类指标。

3. 效率指标:按"一次提问的完整生命周期"算

一个容易漏的点:agentic loop 每一轮都重发整个 context。一个问题触发 3 轮工具调用,同样的历史就被计费 3 次。所以效率必须按生命周期累计,而不是只看一次调用。

指标定义 / 回答什么
input_tokensΣ 各轮 prompt_tokens —— 大头,管理直接优化的对象
output_tokensΣ 各轮 completion_tokens —— 策略基本不影响它,单独计以免污染对比
rounds工具轮数 —— context 质量差会让模型多搜几轮,间接膨胀 input
latency / 管理开销检索、摘要本身的速度与 token 成本(别让省下的被管理调用吃回去)
压缩比实际发送 / 全量历史 —— 管理省了多少(concat=1.0)

input 和 output 分开报告:context 策略几乎只影响 input,且两者单价不同,混在一起会失真。

token 双轨制(关键设计)。上游 API 的 usage 只给一个总量真值,无法分层。要看"哪一层占了多少 token",必须本地用 tiktoken(cl100k_base) 估算。两个数都展示并显示偏差。这个双轨后来立了大功:一次跑批里上游对一个 2.5k 的 context 报出了 132k 的计费,本地估算稳在正常区间——双轨第一天就抓出了上游的计费异常。

4. 准确度指标:两级判定 + 负向探针测幻觉

每个 needle"找到没找到"测两层,因为失败原因完全不同:

  • Context 命中(retrieval-level):needle 所在消息/片段有没有进入最终组装的 context?从结构化报告里按稳定消息 ID 确定性判断,零成本、不需要 LLM。
  • 答案命中(answer-level):模型最终回答里有没有正确事实?事实型针用正则/子串,软性针(决定、偏好类)用 LLM 判分。

两层分开诊断价值极大:context 命中但答案错 → 生成问题(context 太乱、模型被干扰);context 没命中 → 检索/摘要问题。修法完全不同。

幻觉从两个来源计数:① 负向探针——问一个对话里从没出现过的事实("我之前给你的 API key 是多少?"——从没给过),编造即计一次;② context 没命中却给出了具体答案——本该说"不记得"却答了。

这套判定本身后来也被证明有坑:对会改写内容的摘要策略,"context 命中"用精确子串匹配会大量假阴性。这个故事在 Phase 1 报告里——评测体系把自己的盲点也量了出来,正是建尺子的价值。

5. 数据集设计:needle-in-conversation

数据集是把已知事实"针"埋进脚本化的长对话,然后在结尾提问、看系统能不能找回。设计沿几个会导致策略差异的维度铺开,而不是随机埋针:

维度取值测什么
针的类型事实原子 / 决定偏好 / 代码标识符 / 更新型 / 个人事实更新型(先 A 后改 B)测能不能取最新值;代码标识符测纯向量检索弱点
针的位置深度 早/中/晚;载体 user / assistant 长回复中段 / toollost-in-the-middle;assistant 中段针测 chunking
问法直接回忆 / 改写问法 / 隐式依赖 / 负向改写(零词面重叠)专测语义检索;隐式最接近真实使用
干扰项同题材填充 / 近似干扰针 / 负向探针近似干扰("端口 5433"旁放"5432")测精度而非只测召回

题材五个:ML 技术问答、股票/投资、AI 趋势、养花、健康生活,且每个用例单一题材——针和填充同题材才构成真干扰(股票针埋在养花对话里,检索随便就中,分数虚高)。

构造纪律:确定性、可冻结。填充对话用 LLM 生成一次后冻结存文件,永不重新生成;脚本里 assistant 消息写死(不真调 LLM 生成历史),只有最后的 probe 真实跑完整 pipeline。否则两次运行的分数不可比。

6. 两档数据集:smoke 与 long

最初做了 12 个短用例,但很快意识到一个问题——它们的历史只有 ~1.5k token,任何合理窗口都装得下,测不出压缩策略的区分度。这不是用着用着才发现,而是能预判:Phase 1 一上线它就失效。于是分两档:

档位规模职责
smoke12 用例,历史 ~1.5k tok快、便宜,管道/模型/裁判的快速回归自检
long6 用例,历史 ~8.7k tok,assistant 针回复 800+ 字、针埋中段真正压测压缩/chunking 的尺子

采用 augment 而非 replace:加新档不动旧档,保持纵向可比;结果文件带 dataset_version 字段,换 set 必须 bump,不同版本分数不可直接比。long tier 还经过独立 reviewer 审计——它抓出一个真实的尾部泄漏(某个针的旧值在对话尾部被复述,会让 recency 策略"作弊"通过),据此把那个探针换了个不泄漏的针;还让裸数字正则加了数字边界。数据集也要被 review,不是写完就完。

7. 落地时的 learning

  • 被测模型不能用 agent 封装。最初用应用默认的 supermind-agent-v1,它在上游自跑 agentic loop——我们发 2.5k context,它计费报 100k+,还偶发返回空 content,两者都污染指标。eval 默认换成普通 chat 模型(deepseek-v4-pro / grok-4-fast)。
  • 裁判模型会误判,要验。deepseek-v4-flash 当裁判会把明显符合 rubric 的回答判 NO(实测假阴性);换成 kimi-k2.5 可靠。裁判的原始输出存进结果 JSON 的 judge_raw 字段,可审计。
  • 双轨 token 抓异常。见 §3,API 计费偶发暴涨,本地估算更稳健,两者并列才看得出问题。
  • tool result 是 context 污染的大头。read_page 一次能塞进几千 token,每条 tool result 单独记 token、在可视化里打 +N tok 徽章,一眼看出谁在撑爆下一轮。

9. 这把尺子带来了什么

有了它,Phase 1 才有了客观结论:window_summary 用 ~57% 的 token 节省换约 9 个百分点准确度、幻觉零增长(详见 Phase 1 报告)。更意外的是,这套体系在第一次量真实摘要时,把自己 ctx_hit 判定的盲点也照了出来,逼着我们把"精确子串"升级成"LLM 判存在"。一把好尺子不只量被测对象,也会量出自己的刻度问题。

10. 收获清单

  • 效率和准确度必须一起读——单看任何一条都能被极端策略骗过。
  • 效率按提问生命周期累计,input/output 分开;token 走双轨(本地估算分层 + API 真值),双轨能抓上游异常。
  • 准确度两级判定(context 命中确定性 + 答案命中);幻觉靠负向探针,不靠感觉。
  • 数据集要确定性冻结、单题材、按维度铺开、分档(smoke 快测 / long 压测),而且要被 review。
  • 评测的两个外部变量——被测模型和裁判模型——都要验,别用 agent 封装、别信没验过的裁判。
  • 把测量做成结构化数据 + 可视化,而不是日志,排查"模型为什么不知道 X"才有抓手。
