给上下文管理造一把尺子:评测体系从设计到落地的迭代

📅 2026-06-11 ~ 06-22 🏷 needle eval · 工具结果维度 📊 四 tier 矩阵 · 双轴指标 · debugger 可视化

在动手改上下文管理之前,我们先花了几天造一把尺子。这篇讲的不是某个策略,而是怎么量:两条评测轴怎么定、token 和准确度的指标怎么设计、needle 数据集怎么构造、怎么可视化,以及落地时踩的坑。一句话动机——你没法改进一个你量不了的东西。

1. 为什么先造尺子

原本的上下文管理是"把整个 session 历史暴力拼接发给 LLM"。我们想升级成分层管理(滑动窗口+摘要 → RAG → 跨 session)。但只要一问"新策略到底省了多少 token、答案有没有变差",就会发现没有任何客观依据——全靠感觉。于是定下原则:测量体系先于任何策略改动上线,先把暴力拼接(concat)这个基线量化清楚,之后所有策略和它对比。concat 永远是满分上限(它带了全部上下文),也是永远可用的回退。

2. 两条轴,必须一起读

评测沿两条轴:效率(token 成本)和准确度(信息找回能力 / 幻觉程度)。关键认知是这两条必须一起报告:

  • 单看效率没有意义——把 context 全删光效率最高;
  • 单看准确度也没有意义——全量 concat 准确度上限最高。

每个策略是这个二维平面上的一个点,好策略 = 准确度不降的前提下省 token。还有一条纪律:效率数字只在固定数据集上可比(不同问题天然体积不同),所以所有策略跑同一套脚本,同一次运行同时产出效率和准确度两类指标。

3. 效率指标:按"一次提问的完整生命周期"算

一个容易漏的点:agentic loop 每一轮都重发整个 context。一个问题触发 3 轮工具调用,同样的历史就被计费 3 次。所以效率必须按生命周期累计,而不是只看一次调用。

指标定义 / 回答什么
input_tokensΣ 各轮 prompt_tokens —— 大头,管理直接优化的对象
output_tokensΣ 各轮 completion_tokens —— 策略基本不影响它,单独计以免污染对比
rounds工具轮数 —— context 质量差会让模型多搜几轮,间接膨胀 input
latency / 管理开销检索、摘要本身的速度与 token 成本(别让省下的被管理调用吃回去)
压缩比实际发送 / 全量历史 —— 管理省了多少(concat=1.0)

input 和 output 分开报告:context 策略几乎只影响 input,且两者单价不同,混在一起会失真。

token 双轨制(关键设计)。上游 API 的 usage 只给一个总量真值,无法分层。要看"哪一层占了多少 token",必须本地用 tiktoken(cl100k_base) 估算。两个数都展示并显示偏差。这个双轨后来立了大功:一次跑批里上游对一个 2.5k 的 context 报出了 132k 的计费,本地估算稳在正常区间——双轨第一天就抓出了上游的计费异常。

4. 准确度指标:两级判定 + 负向探针测幻觉

每个 needle"找到没找到"测两层,因为失败原因完全不同:

  • Context 命中(retrieval-level):needle 所在消息/片段有没有进入最终组装的 context?从结构化报告里按稳定消息 ID 确定性判断,零成本、不需要 LLM。
  • 答案命中(answer-level):模型最终回答里有没有正确事实?事实型针用正则/子串,软性针(决定、偏好类)用 LLM 判分。

两层分开诊断价值极大:context 命中但答案错 → 生成问题(context 太乱、模型被干扰);context 没命中 → 检索/摘要问题。修法完全不同。

幻觉从两个来源计数:① 负向探针——问一个对话里从没出现过的事实("我之前给你的 API key 是多少?"——从没给过),编造即计一次;② context 没命中却给出了具体答案——本该说"不记得"却答了。

这套判定本身后来也被证明有坑:对会改写内容的摘要策略,"context 命中"用精确子串匹配会大量假阴性。这个故事在 Phase 1 报告里——评测体系把自己的盲点也量了出来,正是建尺子的价值。

5. 数据集设计:needle-in-conversation

数据集是把已知事实"针"埋进脚本化的长对话,然后在结尾提问、看系统能不能找回。设计沿几个会导致策略差异的维度铺开,而不是随机埋针:

维度取值测什么
针的类型事实原子 / 决定偏好 / 代码标识符 / 更新型 / 个人事实更新型(先 A 后改 B)测能不能取最新值;代码标识符测纯向量检索弱点
针的位置深度 早/中/晚;载体 user / assistant 长回复中段 / toollost-in-the-middle;assistant 中段针测 chunking
问法直接回忆 / 改写问法 / 隐式依赖 / 负向改写(零词面重叠)专测语义检索;隐式最接近真实使用
干扰项同题材填充 / 近似干扰针 / 负向探针近似干扰("端口 5433"旁放"5432")测精度而非只测召回

题材五个:ML 技术问答、股票/投资、AI 趋势、养花、健康生活,且每个用例单一题材——针和填充同题材才构成真干扰(股票针埋在养花对话里,检索随便就中,分数虚高)。

构造纪律:确定性、可冻结。填充对话用 LLM 生成一次后冻结存文件,永不重新生成;脚本里 assistant 消息写死(不真调 LLM 生成历史),只有最后的 probe 真实跑完整 pipeline。否则两次运行的分数不可比。

6. 数据集分档:从 smoke / long 到四 tier 矩阵

最初做了 12 个短用例,但很快意识到——它们的历史只有 ~1.5k token,任何合理窗口都装得下,测不出压缩策略的区分度。这能预判:Phase 1 一上线它就失效。于是分档,并进一步把"分档"抽象成两条正交轴:历史长度 × 工具有无。每个格子只变一个量,专门归因一种失败。

无工具有工具
短历史smoke · 12 例 ~1.5k tok · 管道/模型/裁判快速自检—
中历史—tool-medium · 6 例 ~3.2k tok + 真实工具结果 · 隔离工具膨胀(§9)
长历史long · 6 例 ~8.7k tok · 压测压缩/chunkingresearch · 长历史+多工具 · 集成验收(已登记,待建)

诊断型 tier(smoke / long / tool-medium)每个只变一个量,作用是定位策略为什么挂——是历史压缩没搞定,还是工具结果没搞定;集成型 tier(research)还原最难的真实场景,是验收而非诊断。两类配合用:research 发现"出问题了",再回诊断型 tier 归因。long tier 的 assistant 针回复 800+ 字、针埋中段,专为压测 chunking。

纪律:augment 而非 replace——加新档不动旧档,保持纵向可比;结果文件带 dataset_version 字段,换 set 必须 bump,不同版本分数不可直接比。数据集还要被 review:long tier 经独立 reviewer 审计抓出一个真实的尾部泄漏(某针旧值在对话尾部被复述,会让 recency 策略"作弊"通过),据此换了不泄漏的针、并给裸数字正则加了数字边界;tool-medium 也是被独立 review 抓出"历史过短"才补长的(详见 §9)。数据集也要被 review,不是写完就完。

7. 落地时的 learning

  • 被测模型不能用 agent 封装。最初用应用默认的 supermind-agent-v1,它在上游自跑 agentic loop——我们发 2.5k context,它计费报 100k+,还偶发返回空 content,两者都污染指标。eval 默认换成普通 chat 模型(deepseek-v4-pro / grok-4-fast)。
  • 裁判模型会误判,要验。deepseek-v4-flash 当裁判会把明显符合 rubric 的回答判 NO(实测假阴性);换成 kimi-k2.5 可靠。裁判的原始输出存进结果 JSON 的 judge_raw 字段,可审计。
  • 双轨 token 抓异常。见 §3,API 计费偶发暴涨,本地估算更稳健,两者并列才看得出问题。
  • tool result 是 context 污染的大头。read_page 一次能塞进上万 token(上限 30k 字符,见 §9),每条 tool result 单独记 token、在可视化里打 +N tok 徽章,一眼看出谁在撑爆下一轮。

9. 工具结果维度:tool-medium tier 与一个差点测错的坑

smoke 和 long 的脚本对话只有 user/assistant,实跑探针也不触发工具(avg_rounds=1.0)。这忠实于应用"过去轮次的工具中间结果不持久化"的行为,却留下一个盲点:单次提问的 agentic loop 内部,工具结果(尤其 read_page 一次可达上万 token)才是最大的 context 膨胀源——这正是最初的痛点之一,而我们从没量过。Phase 2 起始补上它:tool-medium tier。

在 §6 那张矩阵里,tool-medium 占"中历史 × 有工具"这一格,专门隔离工具维度:保持中等历史,把变量锁在工具轮上。单一变量纪律很关键——tool-medium 不能又长历史又大工具结果,否则归因又糊了。

确定性靠冻结回放(方案 A)。read_page 实时结果每次不同,会破坏跨运行可比。所以生成时真实捕获、eval 时冻结回放:把预置的 [assistant tool_call, tool result] 直接塞进 loop,再让模型出最终答案。这样只测"context 管理对工具结果的处理"(膨胀、carry、针存活),不掺"模型决定调不调工具"的方差。后端 /debug/run 加一个 tool_rounds 回放参数即可。

坑一:捏造工具结果,会把测量本身测错

构造数据集时为了省事,我一开始复刻了 read_page 的提取逻辑,又凭空捏了一个 web_search 的返回——一个 {"results":[…]} 的小 JSON,约 300 字符。等真去 import 并调用应用的 web_search,才发现真实返回是 {"queries":…,"combined_answer":…,"errors":…} 的完全不同结构,而且 约 22000 字符,不是约 300。

差了约 70 倍——而这个 tier 存在的全部意义就是量工具结果的膨胀。用捏造的 stub,会把一次 web_search 轮的膨胀量级测错近两个数量级、还把结构搞错,产出一份"精确、自信、且错误"的报告。这是最隐蔽的一类 bug:它不报错、数字也好看,只是悄悄把你最想测的那个量给污染了。

解法:评测要冻结某个组件的输出,就用那个组件本身去产出——直接 from main import read_page, web_search、真实调用、把返回原样冻结进用例,只有"针"是手工插入到捕获到的正文里。规则:"格式看着对"不等于"分布对"——大小、嵌套、字段形状都会喂进指标。

坑二:真实工具输出会和埋的针打架

把真 web_search 放在 read_page 针之前,一个"通用统计型"的针就废了:真实搜索"采用率"会涌入几十个真实百分比(连针值 71% 本身都在里面),针不再唯一,模型直接从搜索结果里答、而不是从我们埋针的页面里取。

解法:search → read 的多轮结构只留给专有/内部事实型针(如"我们内部锁定 vLLM 0.6.3"——公网搜不到这个"内部"结论);通用公开统计型针保持单轮 read_page,让针在上下文里保持唯一。真实性(用真工具)与干净归因(针唯一)之间有取舍,要在出题时就设计开,别让它们打架。

历史长度:被独立 review 抓出来

独立 reviewer 审计 tool-medium 时一针见血:历史只有 ~1.5k token、和 smoke 一个量级,违背了"中历史"的承诺——等于"smoke 历史 + 一个大工具结果",变量没隔离干净。据此把六个填充对话从 ~2.5k 抬到 ~3.2k token(稳稳介于 smoke 1.5k 与 long 8.7k 之间)。又一次印证 §6 那句:数据集也要被 review。

顺带把生产的 read_page 上限从 5k 提到 30k(多数页面整页装下,膨胀更真实),并让 eval 与生产共用同一个上限同步重新捕获。最终 baseline(concat / grok-4-fast):ctx 命中 100% · ans 命中 100% · 幻觉 0% · 平均 input 8.7k tok(单工具针探针 ~9–10k,唯一的多轮探针 ~16.6k,膨胀主要来自真实工具结果)——concat 在这一档仍是满分上限,区分度要等 Phase 2 对工具结果做 chunk / 检索才会拉开。

顺手立的两条工程纪律:① 跑过不止一次的检查就该是脚本——把生成 / 校验 / 冒烟(_generate.py / _validate.py / _smoketest.py)落盘随用例一起提交,而不是每次重敲一次性命令,数据集才能确定性重建、重测。② 结果文件是实验记录,配置变了(5k→30k)就重跑、替换旧基线,不手改数字。

10. 这把尺子带来了什么

有了它,Phase 1 才有了客观结论:window_summary 用 ~57% 的 token 节省换约 9 个百分点准确度、幻觉零增长(详见 Phase 1 报告)。更意外的是,这套体系在第一次量真实摘要时,把自己 ctx_hit 判定的盲点也照了出来,逼着我们把"精确子串"升级成"LLM 判存在"。一把好尺子不只量被测对象,也会量出自己的刻度问题。

11. 收获清单

  • 效率和准确度必须一起读——单看任何一条都能被极端策略骗过。
  • 效率按提问生命周期累计,input/output 分开;token 走双轨(本地估算分层 + API 真值),双轨能抓上游异常。
  • 准确度两级判定(context 命中确定性 + 答案命中);幻觉靠负向探针,不靠感觉。
  • 数据集要确定性冻结、单题材、按维度铺开、按四 tier 矩阵(历史长度 × 工具有无)分档——诊断型每格只变一个量、集成型做验收,而且要被 review。
  • 评测的两个外部变量——被测模型和裁判模型——都要验,别用 agent 封装、别信没验过的裁判。
  • 把测量做成结构化数据 + 可视化,而不是日志,排查"模型为什么不知道 X"才有抓手。
  • 评测要冻结某个组件的输出,就用那个组件本身去产出——复刻或捏造会带来未知的分布 gap,而 gap 恰好毁掉你要测的那个量("格式对 ≠ 分布对")。真实工具输出还会和埋的针打架,出题时就要把真实性与干净归因设计开。
