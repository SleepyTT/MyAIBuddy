Phase 1: Sliding Window + Rolling Summary — and a bug the eval harness caught in itself

📅 2026-06-15 🏷 strategy=window_summary 📊 long tier · 24 probes

This is the retrospective for the first of three phases in the context-window management roadmap. The one-line result: rolling summarization trades ~57% fewer tokens for about 9 points of answer accuracy and zero increase in hallucination — but the part more worth writing down is that the first time the eval harness graded a real summary, it exposed a blind spot in its own measurement logic.

1. Background: build the ruler before building the thing

The app used to brute-force concatenate the entire session history into every LLM call. Two pains: lots of irrelevant context wasting tokens; and long replies filling the context window fast, driving hallucination. The plan was layered context management — Phase 1 sliding window + rolling summary, Phase 2 pgvector RAG retrieval, Phase 3 cross-session retrieval + memory.

But before touching any of that, we built a measurement system: a needle-in-conversation dataset (known-fact "needles" planted in scripted long conversations), a batch runner with two-level judging (context-hit / answer-hit, plus negative probes for hallucination), and a visualization in the debugger. Without that ruler, "how many tokens did the new strategy actually save, and did answers get worse" is pure vibes. concat (full concatenation) is kept as the always-perfect ceiling baseline that every new strategy is compared against.

2. The strategy: window keeps the recent, summary keeps the distant

The context assembled for each request has three segments:

[system prompt]
[rolling summary]    ← older history (outside the window) compressed to one block (≤400 tok)
[last N turns verbatim]  ← N=6, preserves coreference ("it", "that thing") and recency
[current user message]

Key designs: the window must be verbatim (coreference resolution can only rely on the original text); the summary updates incrementally (old summary + the few newly-evicted turns → new summary, one cheap LLM call, not a full recompute each time); the summary persists in Chat.summary. Short conversations (≤N turns) have an empty summary and degrade to concat automatically — zero summarization cost.

A structural prerequisite shared by all phases also landed here: context assembly moved from the frontend to the backend. The frontend used to send the full history; now it sends only chat_id and the backend assembles per strategy. /chat (production, reads DB) and /debug/run (eval, stateless, takes history) share one assemble_context — otherwise the eval would measure something different from production, and lose its meaning.

3. How it was built: multi-agent collaboration

This phase was driven by four subagents working in parallel with review loops:

  • dev implemented window_summary per the Phase 1 plan (strategy, backend assembly, model summary columns, context_report summary layer).
  • scientist extended the long-tier dataset per the eval plans (probes 15→24: early precise-value needles to test summary fidelity, low-surface-overlap paraphrase needles to test semantic retrieval).
  • code-reviewer reviewed dev's code diff; dsreviewer reviewed scientist's dataset diff.

dev and scientist touched fully disjoint files (code vs JSON), so they shared a working tree in parallel. Both reviewers returned PASS-WITH-FIXES; each iterated to clean before the eval ran. code-reviewer caught two BLOCKING items that would distort the comparison (compression ratio omitting summary tokens; ctx_hit substring matching too easily on short numeric needles), which dev fixed; dsreviewer had the dataset's bare-number regexes add digit boundaries.

An integration bug caught mid-orchestration: models.py used str | None (Python 3.10+ syntax) while this environment is 3.9 — the server simply wouldn't start. py_compile doesn't flag it (the annotation is evaluated at runtime), and the no-Bash reviewer couldn't run anything — only actually starting the server exposed it. Ironically this exact pitfall was already recorded in reflections, but the cold subagent never read it.

4. First run: the numbers were lying

The eval finished and window_summary looked like a disaster at first glance:

Metricconcatwindow_summary (first run)
ctx-hit100%9%
ans-hit100%77%
hallucination0%71%
input/probe55392672

ctx-hit 9%, hallucination 71% — taken at face value, the conclusion would be "the summary threw away the context and is fabricating wildly." But one thing didn't add up: ans-hit was 77%. If the context truly retained nothing, how did the model answer three-quarters of the questions? That contradiction is the thread that unravels the artifact.

5. Root cause: two measurement bugs

Bug ①: exact substring match is guaranteed to false-negative against a summary that reformats

ctx_hit judged a summary-absorbed needle by checking whether the needle's content string was a literal substring of the summary text. But a rolling summary reformats facts. A concrete case:

Needle:   HybridRetrieverV2（retrieval/service.py）     ← full-width parens
Summary:  …the retrieval entry class is `HybridRetrieverV2`, located at `retrieval/service.py`.
Model:    "Register the new recall path on `HybridRetrieverV2` (file retrieval/service.py)" ✓ correct

The information was fully preserved and the model answered correctly, but the summary added backticks and used "located at" + a comma instead of parentheses — so the exact substring HybridRetrieverV2（retrieval/service.py） is not found in the summary, and it scored a miss. A summary naturally rewords, re-punctuates, and reformats, so this judging massively false-negatives on preserved facts, crushing ctx-hit to 9%.

code-reviewer did look at ctx_hit — but at the opposite direction: short numeric needles (like 242) substring-matching too loosely (a false positive inside 2425), which we fixed with digit boundaries. The real killer was the false-negative direction, and it only shows up when you grade a real summary.

Bug ②: a correct answer was being scored as a hallucination

The hallucination logic was: a negative probe that fabricates → hallucination; or "context-miss and the model gave a confident specific answer" → run the fabrication judge. The flaw: it ran the judge on any context-miss regardless of whether the answer was right, and the fabrication judge only sees question+reply (not ground truth), so it labels a fact correctly recalled from the summary as "fabrication." Stacked on Bug ①'s false context-misses, 14 of 22 needle probes were "answered correctly but flagged as hallucination" — pure false positives. The real hallucination test is the 2 negative probes — both window_summary runs correctly declined.

The deeper realization: a correct answer can never be a hallucination. The original logic was missing that guard.

6. The fix

Don't hand-edit the result JSON (that would falsify the experimental record) — fix the measurement code and re-run, so the corrected numbers are real measured data.

# Bug ②: a correct answer isn't a hallucination — one guard
- elif hit_ctx is False:
+ elif hit_ctx is False and not hit_ans:

# Bug ①: ctx_hit becomes  substring fast-path + LLM fallback
#  · verbatim needles still judged by position (concat stays on this path:
#    zero LLM cost, identical result)
#  · summary-absorbed needle: a substring/boundary match = definitely present
#    (fast-path, no LLM)
#  · on substring failure, fall back to an LLM: "is this fact retained in the
#    summary (different wording/format still counts)?"

The LLM judge only fires when the substring fails, so the cost is bounded; concat, whose needles are all verbatim, never reaches the summary branch — unaffected and with no added LLM calls.

The real Phase 1 trade-off: window_summary spends ~57% fewer tokens for about 9 points of accuracy (100%→91%) and zero increase in hallucination. Far more favorable than the artifact-laden first read suggested.

The remaining genuine misses are all explainable and, crucially, none are hallucinations: one run's summary genuinely failed to keep a class name and the model correctly declined; another scored a ctx-miss yet the model answered the gist correctly (the summary kept enough to answer, but not enough for the ctx judge to call it "fully retained"); and one had the info in the summary (ctx-hit) but the answer wrapped the value in **8** markdown bold that the regex didn't match (a dataset-level brittleness).

The 16.4s latency should be discounted: the stateless eval recomputes the summary from scratch for every probe; production /chat keeps a persisted rolling summary updated incrementally, so per-question latency is far lower. Also the summary is an LLM call, so there is run-to-run variance (under a different random summary before the fix, ans-hit was 77%; this run 91%) — serious comparison should average several runs.

8. Takeaways

  • End-to-end evaluation surfaces blind spots in the measurement system itself. This ruler exists to score strategies; the first time it measured a real summary, it measured the flaws in its own ctx_hit/hallucination judging — which is exactly why you build the ruler.
  • For systems that reformat content, exact substring matching is the wrong judge. For summaries / RAG / rewriting, facts get reworded; "is this fact present?" is a semantic question — use an LLM judge (and keep substring as a cheap positive shortcut).
  • A correct answer is never a hallucination. The hallucination check must be predicated on the answer being wrong.
  • Integration testing > compile + static review. The str | None crash on 3.9 wasn't caught by py_compile or a no-Bash reviewer — only by actually starting the server. And cold subagents miss already-documented pitfalls, so "actually run it" is non-skippable.
  • Diagnose from the contradiction. "ctx 9% but ans 77%" — the inconsistency was the entry point to unmasking the artifact. When metrics disagree with each other, suspect the measurement first.
