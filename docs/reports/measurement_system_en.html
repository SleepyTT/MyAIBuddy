Building a Ruler for Context Management: how the eval system went from design to implementation

📅 2026-06-11 – 06-22 🏷 needle eval · tool-result dimension 📊 four-tier matrix · two-axis metrics · debugger viz

Before touching context management at all, we spent a few days building a ruler. This post isn't about any one strategy — it's about how to measure: how the two evaluation axes are defined, how the token and accuracy metrics are designed, how the needle dataset is constructed, how it's visualized, and the potholes hit along the way. The one-line motivation: you can't improve what you can't measure.

1. Why build the ruler first

Context management used to be "brute-force concatenate the whole session history into the LLM." We wanted to upgrade to layered management (sliding window + summary → RAG → cross-session). But the moment you ask "how many tokens did the new strategy actually save, and did answers get worse," you find there's no objective basis — only vibes. So the rule: the measurement system ships before any strategy change; quantify the brute-force concatenation (concat) baseline first, then compare everything against it. concat is forever the perfect ceiling (it carries the full context) and the always-available fallback.

2. Two axes, read together

Evaluation runs along two axes: efficiency (token cost) and accuracy (information recall / hallucination). The key insight is that they must be reported together:

  • Efficiency alone is meaningless — deleting all context maximizes it;
  • Accuracy alone is meaningless — full concat maximizes it.

A strategy is a point in this 2-D plane, and a good strategy is one that saves tokens without dropping accuracy. One discipline follows: efficiency numbers are only comparable on a fixed dataset (different questions have inherently different sizes), so every strategy runs the same scripts, and a single run produces both efficiency and accuracy metrics at once.

3. Efficiency metrics: account over a question's full lifecycle

An easy thing to miss: the agentic loop resends the entire context every round. A question that triggers 3 tool-call rounds bills the same history 3 times. So efficiency must accumulate over the lifecycle, not just one call.

MetricDefinition / what it answers
input_tokensΣ prompt_tokens per round — the big one, what management directly optimizes
output_tokensΣ completion_tokens per round — barely affected by strategy, counted separately so it doesn't pollute the comparison
roundstool-call rounds — bad context makes the model search more, inflating input indirectly
latency / mgmt overheadthe speed and token cost of retrieval/summarization itself (don't let the saved tokens get eaten by the management call)
compression ratioactually-sent / full history — how much management saved (concat = 1.0)

input and output are reported separately: context strategy almost only affects input, and the two have different unit prices, so mixing them distorts.

Dual-track token counting (a key design). The upstream API's usage gives only a single ground-truth total — it can't break down by layer. To see "how many tokens each layer took," you must estimate locally with tiktoken (cl100k_base). Both numbers are shown, with the deviation. This dual track later earned its keep: in one batch run the upstream reported 132k billed tokens for a 2.5k context, while the local estimate stayed in the normal range — the dual track caught an upstream billing anomaly on day one.

4. Accuracy metrics: two-level judging + negative probes for hallucination

Whether a needle was "found" is tested at two levels, because the failure causes are entirely different:

  • Context-hit (retrieval level): did the needle's message/fragment make it into the assembled context? Judged deterministically by stable message ID from the structured report — zero cost, no LLM.
  • Answer-hit (answer level): does the final reply contain the correct fact? Factual needles use regex/substring; soft needles (decisions, preferences) use an LLM judge.

Splitting the two is hugely diagnostic: context-hit but answer-wrong → a generation problem (context too noisy, model distracted); context-miss → a retrieval/summary problem. The fixes are completely different.

Hallucination is counted from two sources: ① negative probes — ask about a fact that never appeared in the conversation ("what was the API key I gave you?" — never given); fabricating one counts; ② context-miss yet a confident specific answer — it should have said "I don't recall" but answered anyway.

This judging itself later proved to have a pitfall: for a summarization strategy that reformats content, judging "context-hit" by exact substring match massively false-negatives. That story is in the Phase 1 report — the eval system measured a blind spot in itself, which is exactly the point of building the ruler.

5. Dataset design: needle-in-conversation

The dataset plants known-fact "needles" into scripted long conversations, then asks at the end and checks whether the system recovers them. The design spreads along dimensions that actually cause strategy differences, rather than planting needles at random:

DimensionValuesWhat it tests
Needle typefactual atom / decision & preference / code identifier / update-type / personal factupdate-type (A then corrected to B) tests fetching the latest value; code identifier tests the weak spot of pure vector retrieval
Needle positiondepth early/mid/late; carrier user / mid-reply in a long assistant message / toollost-in-the-middle; mid-reply needles test chunking
Question styledirect recall / paraphrase / implicit dependency / negativeparaphrase (zero surface overlap) tests semantic retrieval; implicit is closest to real use
Distractorssame-topic filler / near-miss needles / negative probesnear-miss ("port 5433" next to "5432") tests precision, not just recall

Five topics: ML technical Q&A, stocks/investing, AI trends, gardening, healthy living — and one topic per case: needles and filler must share a topic to form real interference (a stock needle buried in a gardening conversation is trivially retrievable, inflating the score).

Construction discipline: deterministic, freezable. Filler conversations are LLM-generated once and then frozen to a file, never regenerated; the assistant messages in the script are hard-coded (history is not generated by a live LLM), and only the final probe runs the full pipeline for real. Otherwise two runs aren't comparable.

6. Dataset tiers: from smoke / long to a four-tier matrix

We first wrote 12 short cases, but quickly realized — their histories are only ~1.5k tokens, which any reasonable window fits, so they can't differentiate compression strategies. This was predictable: the moment Phase 1 ships, they're useless. So we tiered the dataset, and then abstracted "tiering" into two orthogonal axes: history length × tools-or-not. Each cell varies one thing only, attributing one kind of failure.

No toolsWith tools
Short historysmoke · 12 cases ~1.5k tok · pipeline/model/judge sanity—
Medium history—tool-medium · 6 cases ~3.2k tok + real tool results · isolates tool-result bloat (§9)
Long historylong · 6 cases ~8.7k tok · compression/chunking stressresearch · long history + multi-tool · integration acceptance (registered, not yet built)

Diagnostic tiers (smoke / long / tool-medium) each vary one thing, to locate why a strategy breaks — was it history compression or tool-result handling; the integration tier (research) reproduces the hardest real scenario, for acceptance, not diagnosis. The two work together: research finds "something's wrong," then you go back to a diagnostic tier to attribute it. The long tier's 800+ char assistant needle replies, with needles mid-reply, are built to stress chunking.

Discipline: augment, don't replace — a new tier leaves the old one intact, preserving longitudinal comparability; result files carry a dataset_version field that must be bumped on any set change, and scores across versions aren't directly comparable. Datasets also get reviewed: the long tier's independent reviewer audit caught a real tail-leak (one needle's old value restated near the end, letting a recency strategy "cheat" past it), so that probe was re-pointed at a non-leaking needle and the bare-number regexes gained digit boundaries; tool-medium was likewise review-caught for "histories too short" and then lengthened (see §9). Datasets get reviewed too — not done when written.

7. Implementation learnings

  • The model under test can't be an agent wrapper. We first used the app's default supermind-agent-v1, which runs its own agentic loop upstream — we send a 2.5k context and it bills 100k+, and it occasionally returns empty content, both polluting the metrics. The eval defaults to a plain chat model (deepseek-v4-pro / grok-4-fast).
  • Judge models misjudge — verify them. deepseek-v4-flash as judge scored clearly rubric-compliant answers as NO (verified false negatives); kimi-k2.5 is reliable. The judge's raw output is stored in the result JSON's judge_raw field for auditing.
  • Dual-track tokens catch anomalies. See §3 — upstream billing occasionally spikes; the local estimate is more robust, and you only see the problem with both side by side.
  • Tool results are the main context polluter. read_page can inject tens of thousands of tokens at once (30k-char cap, see §9); each tool result's token count is recorded separately and shown as a +N tok badge in the visualization, so you see at a glance who's blowing up the next round.

It reads the self-contained result JSON produced by the CLI batch runner and renders three blocks: ① a strategy comparison table (one row per strategy: ctx-hit, ans-hit, hallucination, input/output tokens, rounds, latency); ② a dimension drill-down (hit rate bucketed by depth/carrier/style, red below threshold — tells you why it lost); ③ a probe list (per-probe ctx/ans/hallucination badges). Architecture: CLI batch + debugger to view. The backend adds only two read-only endpoints (list files, read file).

9. The tool-result dimension: the tool-medium tier and a metric we almost got wrong

The smoke and long scripts contain only user/assistant turns, and live probes don't trigger tools either (avg_rounds=1.0). That's faithful to the app's behavior ("intermediate tool results from past rounds aren't persisted"), but it leaves a blind spot: inside a single question's agentic loop, the tool results — especially read_page, which can reach tens of thousands of tokens in one shot — are the biggest source of context bloat. That's one of the original pain points, and we'd never measured it. Phase 2 opens by filling it: the tool-medium tier.

In §6's matrix, tool-medium occupies the "medium history × with tools" cell, isolating the tool dimension: keep the history medium, lock the variable onto the tool round. The single-variable discipline matters — tool-medium must not be both long-history and big-tool-result, or attribution blurs again.

Determinism via frozen replay (method A). Live read_page results differ every time, which would break cross-run comparability. So we capture for real at build time, then freeze-replay at eval time: the preset [assistant tool_call, tool result] is injected straight into the loop, then the model is asked for a final answer. This measures only "how context management handles the tool result" (bloat, carry, needle survival), without the variance of "did the model decide to call a tool." The backend just adds a tool_rounds replay parameter to /debug/run.

Pitfall #1: fabricating tool results miscalibrates the measurement itself

To save effort while building the dataset, I first re-implemented read_page's extraction and invented a web_search return — a small {"results":[…]} JSON, ~300 chars. When I actually imported and called the app's web_search, the real payload turned out to be a completely different shape, {"queries":…,"combined_answer":…,"errors":…}, and ~22,000 chars, not ~300.

A ~70× gap — and measuring tool-result bloat is the entire reason this tier exists. The fabricated stub would have mis-sized a web_search round by nearly two orders of magnitude and gotten its structure wrong, producing a "precise, confident, and wrong" report. This is the most insidious class of bug: it doesn't error, the numbers look fine, it just silently corrupts the very quantity you most wanted to measure.

Fix: when an eval freezes the output of a component, produce it with that component itself — from main import read_page, web_search, call them for real, freeze the return verbatim into the case; only the "needle" is hand-inserted into the captured body. Rule: "the format looks right" ≠ "the distribution is right" — size, nesting, and field shape all feed the metric.

Pitfall #2: real tool output competes with the planted needle

Put a real web_search in front of a read_page needle and a "generic-statistic" needle breaks: a real search for "adoption rate" floods the context with dozens of real percentages (including the needle value 71% itself), the needle is no longer distinctive, and the model answers from the search blob instead of from the page we planted the needle in.

Fix: reserve the search → read multi-round shape for specific/internal-fact needles (e.g. "our pinned version is vLLM 0.6.3" — a public search won't surface that "internal" conclusion); keep generic public-statistic needles single-round read_page so the needle stays unique in context. Realism (real tools) and clean attribution (a unique needle) trade off — design the question/needle so they don't collide.

History length: caught by independent review

The independent reviewer auditing tool-medium nailed it: histories were only ~1.5k tokens, smoke-sized, breaking the "medium history" promise — effectively "smoke history + one big tool result," with the variable not cleanly isolated. So the six filler conversations were lengthened from ~2.5k to ~3.2k tokens (comfortably between smoke's 1.5k and long's 8.7k). Another vindication of §6's line: datasets get reviewed too.

Along the way we raised the production read_page cap from 5k to 30k (whole page in most cases, more realistic bloat) and re-captured with eval and production sharing the same cap. Final baseline (concat / grok-4-fast): ctx-hit 100% · ans-hit 100% · hallucination 0% · avg input 8.7k tok (single-tool-needle probes ~9–10k, the one multi-round probe ~16.6k, the bloat coming mostly from real tool results) — concat is again the perfect ceiling on this tier; differentiation waits for Phase 2 to chunk/retrieve over tool results.

Two engineering disciplines, picked up along the way: ① a check you run more than once should be a script — the generate / validate / smoke-test (_generate.py / _validate.py / _smoketest.py) live next to the cases and are committed with them, not re-typed as one-off commands, so the dataset can be rebuilt and re-verified deterministically. ② A result file is an experimental record: when config changed (5k→30k) we re-ran and replaced the old baseline rather than hand-editing numbers.

10. What the ruler bought us

With it, Phase 1 finally has an objective conclusion: window_summary spends ~57% fewer tokens for about 9 points of accuracy and zero hallucination increase (see the Phase 1 report). More unexpectedly, the first time this system measured a real summary it exposed a blind spot in its own ctx_hit judging, forcing us to upgrade "exact substring" to "LLM presence judge." A good ruler doesn't just measure the thing under test — it surfaces problems in its own markings.

11. Takeaways

  • Efficiency and accuracy must be read together — either one alone can be gamed by an extreme strategy.
  • Account efficiency over the question lifecycle, input/output separate; count tokens on a dual track (local per-layer estimate + API ground truth), which catches upstream anomalies.
  • Judge accuracy at two levels (deterministic context-hit + answer-hit); measure hallucination with negative probes, not by feel.
  • Datasets must be deterministically frozen, single-topic, spread across dimensions, tiered by a four-tier matrix (history length × tools-or-not) — diagnostic tiers vary one thing each, the integration tier does acceptance — and reviewed.
  • The two external variables in evaluation — the model under test and the judge model — both need verification; don't use an agent wrapper, don't trust an unverified judge.
  • Make measurement structured data + visualization, not logs, so "why doesn't the model know X" is actually debuggable.
  • When an eval freezes a component's output, produce it with that component itself — re-implementing or fabricating it introduces an unknown distribution gap that corrupts the very quantity you're measuring ("format right ≠ distribution right"). Real tool output also competes with planted needles, so design realism vs clean attribution apart from the start.
