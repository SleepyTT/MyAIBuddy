My AI Buddy · 上下文管理 · 阶段总结

Phase 1：滑动窗口 + 滚动摘要,以及一次评测体系给自己挑出的 bug

📅 2026-06-15 🏷 strategy=window_summary 📊 long tier · 24 探针

这是 context window 管理三阶段路线里第一阶段的技术总结。核心结论一句话:滚动摘要用 57% 的 token 节省 换来约 9 个百分点 的准确度下降、零 幻觉增长——但更值得写下来的,是评测体系在第一次跑真实摘要时,把自己测量逻辑里的盲点照了出来。

1. 背景:为什么先建尺子,再造东西

应用原本把一个 session 里的全部对话历史暴力拼接发给 LLM,有两个痛点:大量无关 context 费 token;长回答迅速撑满 context window 导致幻觉。计划用分层 context 管理来解决——Phase 1 滑动窗口+滚动摘要,Phase 2 pgvector RAG 检索,Phase 3 跨 session 检索+记忆。

但在动手之前,我们先建了一套评测体系:一个 needle-in-conversation 数据集(把已知事实"针"埋进脚本化长对话)、一个两级判定的跑批器(context 命中 / 答案命中,外加负向探针测幻觉)、以及 debugger 里的可视化。没有这把尺子,"新策略到底省了多少 token、答案有没有变差"就只能靠感觉。concat(全量拼接)作为永远满分的天花板基线保留,所有新策略和它对比。

2. 策略:窗口保近、摘要保远

每次请求组装的 context 分三段:

[system prompt]
[滚动摘要]        ← 把"窗口之外"的旧历史压缩成一段(≤400 token)
[最近 N 轮原文]    ← N=6,保证指代("它"、"刚才那个")和近期连贯
[当前用户消息]

关键设计:窗口必须是原文(指代消解只能靠原文);摘要增量更新(旧摘要 + 新滑出的几轮 → 新摘要,一次便宜 LLM 调用,而非每次从全量重算);摘要持久化在 Chat.summary。短对话(≤N 轮)摘要为空,自动退化成 concat,不付任何摘要成本。

一个所有阶段共享的架构前提也在这一步完成了:context 组装从前端搬到后端。原来前端发全量 history,现在前端只发 chat_id,后端按 strategy 组装。/chat(线上,读 DB)和 /debug/run(评测,无状态收 history)共用同一个 assemble_context——否则评测量的和线上跑的不是同一个东西,评测就失去意义。

3. 怎么造的:多 agent 协作

这一阶段用了四个子 agent 并行+评审的方式推进:

  • dev 按 Phase 1 计划实现 window_summary(策略、后端组装、模型摘要列、context_report 摘要层)。
  • scientist 按各阶段评测计划扩充 long tier 数据集(探针 15→24:早期精确值针测摘要保真、低词面重叠 paraphrase 针测语义检索)。
  • code-reviewer 审 dev 的代码 diff,dsreviewer 审 scientist 的数据集 diff。

dev 和 scientist 改的文件完全不相交(代码 vs JSON),所以可以共享工作树并行。两个 reviewer 都给了 PASS-WITH-FIXES,各自迭代到清干净才进入评测。code-reviewer 抓到两个会扭曲对比的 BLOCKING(压缩比漏算摘要 token、ctx_hit 短数字针易误命中),dev 修复;dsreviewer 让数据集的 bare 数字正则加了数字边界。

编排途中抓到的集成 bug:models.py 用了 str | None(Python 3.10+ 语法),而本环境是 3.9,服务器直接起不来。这个 py_compile 不报(注解是运行时才求值)、无 Bash 的 reviewer 也跑不出来——只有真正启动服务器才暴露。讽刺的是这个坑早就记在 reflections 里,但冷启动的子 agent 没读到。

4. 第一次跑分:数字在撒谎

评测跑完,window_summary 的结果乍看是灾难:

指标concatwindow_summary(首跑)
ctx 命中100%9%
ans 命中100%77%
幻觉率0%71%
input/题55392672

ctx 命中 9%、幻觉 71%——如果照单全收,结论会是"摘要把上下文丢光了,而且疯狂编造"。但有个地方对不上:ans 命中却有 77%。如果 context 真的什么都没保住,模型怎么答对了四分之三?这个矛盾是揭穿伪影的线索。

5. 根因:两个测量 bug

Bug ①:精确子串匹配,在会改写的摘要面前必然假阴性

ctx_hit 对"被摘要吸收的针"的判定方式是:针的内容字符串是否精确子串出现在摘要文本里。但滚动摘要是会改写事实的。实锤一例:

针内容:  HybridRetrieverV2（retrieval/service.py）     ← 全角括号
摘要文本:  …检索代码入口类为 `HybridRetrieverV2`,位于 `retrieval/service.py`。
模型回答:  新加一路召回的注册点是 `HybridRetrieverV2`(文件 retrieval/service.py)✓ 答对

信息完整保留了,模型也答对了,但摘要加了反引号、用"位于"和逗号代替括号——精确子串 HybridRetrieverV2（retrieval/service.py） 在摘要里找不到,于是判 miss。摘要天然会换措辞、换标点、换格式,所以这种判定对保留下来的事实大面积假阴性,ctx 命中被压到 9%。

code-reviewer 当时其实盯了 ctx_hit,但盯的是反方向——短数字针(如 242)子串匹配太松会假阳性(命中 2425 里的 242),我们加了数字边界修掉了。真正的杀手是假阴性方向,它只有在跑一次真实摘要时才暴露。

Bug ②:答对的回答被记成幻觉

幻觉判定的逻辑是:负向探针编造 → 幻觉;或者"ctx-miss 且模型给了自信的具体回答"→ 调编造裁判。问题在于它不看回答对错就在 ctx-miss 时触发裁判,而编造裁判只看问答、不知道真值,把"从摘要里正确回忆出来的答案"也判成了"编造"。叠加 Bug ① 的假 ctx-miss,22 个 needle 探针里 14 个是"答对却被记为幻觉"的纯假阳性。真正的幻觉测试是 2 个负向探针——两个 window_summary 都正确拒答了。

更根本的认知:一个正确的回答永远不可能是幻觉。原逻辑缺了这条守卫。

6. 修复

不手改结果 JSON(那等于篡改实验记录),而是修测量代码、重跑,让正确数字成为真测出来的数据。

# Bug ②:答对不算幻觉 —— 一行守卫
- elif hit_ctx is False:
+ elif hit_ctx is False and not hit_ans:

# Bug ①:ctx_hit 改为 子串快速路径 + LLM 回退
#  · verbatim 针仍按 position 判定(concat 全走这条,零 LLM 开销、结果不变)
#  · 被摘要吸收的针:子串/数字边界命中即确定(快速路径,无 LLM)
#  · 子串失败时回退 LLM:"这条事实在摘要里是否保留(措辞格式不同也算)?"

LLM 判定只在子串失败时触发,开销可控;concat 因为针全是 verbatim,根本走不到摘要分支,既不受影响也不加任何 LLM 调用。

7. 修正后的结果

ctx 命中100%9%91%
ans 命中100%77%91%
幻觉率0%71%0%
input/题553926722394
压缩比1.00.370.38
延迟1.7s16.4s16.4s
真实的 Phase 1 权衡:window_summary 用 ~57% 的 token 节省,换约 9 个百分点的准确度(100%→91%)、幻觉零增长。比伪影满天飞的首读乐观得多。

剩余的真实 miss 也都解释得通、且都不是幻觉:某一轮摘要确实没保住一个类名,模型正确地拒答了;另一例 ctx 判 miss 但模型答对了大意(摘要保留了够回答的信息、但不足以让 ctx 裁判判"完整保留");还有一例信息在摘要里但回答带了 **8** 的 markdown 加粗、正则没匹配上(数据集层面的小脆弱)。

延迟那 16.4s 要打折看:无状态评测每个探针都从头重算摘要;线上 /chat 是持久化的滚动摘要、只增量更新,单问延迟远低于此。另外摘要是 LLM 调用,有轮间方差(修正前那次随机摘要下 ans 命中是 77%,这次 91%)——严肃对比宜多跑取均值。

8. 收获

  • 端到端评测会照出测量体系自己的盲点。这套尺子是用来给策略打分的,结果第一次量真实摘要,就把ctx_hit/幻觉判定自己的缺陷量了出来——这正是建尺子的价值。
  • 对会改写内容的系统,精确子串匹配是错的判定方式。摘要/RAG/改写类输出,事实会换措辞;判"信息在不在"是个语义问题,该用 LLM 判定(并用子串做正向快速路径省钱)。
  • 一个正确的回答永远不是幻觉。幻觉判定必须以回答错误为前提。
  • 集成测试 > 编译 + 静态审查。str | None 的 3.9 崩溃,py_compile 不报、无 Bash 的 reviewer 看不出,只有真起服务器才暴露。冷启动的子 agent 还会漏掉已记录在案的项目坑——所以"真的把它跑起来"这一步不能省。
  • 诊断从矛盾开始。"ctx 9% 但 ans 77%"这个对不上的地方,就是拆穿伪影的入口。数字之间不自洽时,先怀疑测量。

9. 下一步
