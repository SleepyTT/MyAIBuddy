Phase 1.5：给预算装上旋钮,把"被迫取舍"逼出来——一个反直觉的结论

📅 2026-06-22 🏷 context budget sweep 📊 20 格网格 · 2 策略 × 2 tier × 5 预算

我们做了 needle 数据集、四 tier 矩阵、工具结果维度——但有一个指标一直是 0:幻觉。不是模型不幻觉,是没有任何 case 把上下文逼到"装不下、必须丢"的地步(全程远不到 128k)。这篇讲我们怎么把 context 预算做成可调旋钮,在紧预算下逼出"被迫取舍",第一次量出幻觉,并撞上一个反直觉的结果:工具结果里的具体事实,我们测过的两种盲压缩(摘要、截断)都救不了。这指向——但还没证明——需要 query 感知的检索(RAG),那是 Phase 2 要去验证的假设,本轮没测它,不下结论。

1. 缺的那个 regime:被迫溢出

到目前为止的评测只覆盖了一种场景——"自愿压缩省钱":上下文装得下,策略主动丢一些以省 token。但生产里幻觉真正高发的是另一种:上下文逼近/超过可用预算 → 模型被迫做 context 管理 → 丢了关键信息 → 该说"不记得"却编一个出来。这个 regime 我们从没测过,因为所有数据集全程都塞得进 128k。

一个差点白做的坑:CONTEXT_LIMIT=128k 当时只是个"显示数字"。它只用来算"利用率 %",策略本身不读它——window_summary 是按轮数(WINDOW_TURNS=6)切的,不是按 token 切的。所以单把这个常数调小,什么都不会变。真正要做的不是改一个数,而是让策略变成 budget-aware(按 token 预算压)。这也顺带让 window_summary 更贴近现实:按轮数切本就不合理——一条 30k 的工具结果和一句"好的"各算一轮。

2. 让策略 budget-aware

预算 B 是一次 prompt 的 token 上限。组装按优先级填,先保命、再压可压的:当前问题 + tools schema(必保)> loop 内工具结果(高)> 最近历史(verbatim 窗口)> 更早历史(摘要 / 丢弃)。三个策略各按自己的哲学在预算压力下退化:

策略预算不足时对"当前问题"
concat截断:头截断超预算的工具结果、丢最老的历史(不摘要)位置盲
window_summarytoken 窗口(≤ WINDOW_TURNS,再按预算收) + 把挤出的历史和超预算工具结果做摘要query 盲
RAG(Phase 2)切块 + 按问题检索 top-k 填进预算query 感知
关键不变量与方法。① 预算是横切 eval 参数,不是新 tier——复用现有 long / tool-medium 在 5 个预算下跑,区分度从预算里来,不必造新数据。② 默认 B=128k → 行为与改造前逐字节一致(已验证:concat 默认 == 旧 assemble_context),旧基线不受影响。结果带 context_budget 字段 + run_id 后缀(_b8k),同数据集不同预算可并排比。

3. 结果:20 格网格

⚠️ 这批数字来自重设计前的实现。2026-06-23 已按工业界做法重写组装层(历史纯 token 驱动、去掉 6 轮硬帽子;工具结果改为固定 1k 配额;新增主动省钱旋钮)。tool-medium 那两行尤其会变(新版 concat 头截断到 1k 几乎恒丢中段针 ctx≈0、window 盲摘要也大概率丢针),待重跑后替换。下面三个**定性发现**(溢出 regime 激活、历史维度 window>concat、盲压缩对工具针都不行)预计仍成立。

model=grok-4-fast,judge=kimi-k2.5,2 策略 × 2 tier × 5 预算。格内为 ctx 命中 / ans 命中 / 幻觉:

策略 · tier128k32k16k8k4k
concat · long1.0/.95/01.0/.95/01.0/.95/0.55/.59/.17.18/.32/.38
window_summary · long.86/.86/0.95/.95/0.91/.82/0.91/.95/01.0/.95/0
concat · tool-medium1.0/.83/01.0/1.0/01.0/1.0/0.83/.83/0.67/.50/0
window_summary · tool-medium1.0/1.0/01.0/1.0/01.0/1.0/0.50/.67/.12.17/.17/.38
读这张表的前提:很多格子里"预算根本没咬上"。所谓咬(binding) = 预算 B 小于策略本来就会发送的大小,才逼它多丢东西。我们的数据下:window_summary 靠 WINDOW_TURNS=6 已经压到 ~3.4k,所以它在 8k–128k 这几档预算全没咬(发送量几乎不变),这几格是同一配置的噪声重复采样,不是预算效应;tool-medium 全量也才 ~16k,所以 32k 以上对它也不咬。

再叠三个噪声源——单次跑(没重复平均)、window_summary 每轮实时摘要(文本每次不同)、ctx/ans 的 LLM 裁判(非确定)——加上样本小(tool-medium 只 6 个针探针,翻 1 个就是 .17),非咬格子的上下浮动就是这个噪声底,不是趋势。直接证据:同一个 (concat, tool-medium, 128k) 配置我们恰好跑了两次,一次 ans 1.0、一次 .83——同样输入、不同结果。所以「window_summary·long 4k 反而最高」「concat·tool-medium 128k 比 32k 低」都是噪声,不是"预算越少越好"。

只把"咬上了"的格子当信号读(粗体那些):concat·long 8k/4k、concat·tool-medium 8k/4k、window_summary·tool-medium 8k/4k——那里预算真把信息逼丢了,趋势单调清晰。要给非咬区也得到干净结论,得每格重复跑 N 次取均值±区间,或把预算压到各策略自然大小以下(window_summary 要 <3k 才咬)。

4. 三个发现

① 溢出 regime 被激活,幻觉指标第一次有信号

concat·long 随预算收紧一路崩:128k–16k 全装下(ctx 1.0、幻觉 0)→ 8k 开始丢历史(ctx .55、幻觉 .17)→ 4k 重截(ctx .18、幻觉 .38)。这正是预判的因果链——预算不足 → 被迫丢信息 → 模型编造。此前所有 tier 幻觉恒为 0,现在终于量出来了。

② 历史维度:window_summary 完胜 concat(验证假设)

紧预算下的 long:concat 崩(ctx .55→.18、幻觉冲到 .38),而 window_summary 全程 ctx .91–1.0、幻觉 ~0,且 token 只有 concat 的一半(~2.5k vs 5k+)。因为摘要把挤出窗口的历史压缩保留了,concat 直接丢整轮。

③ 工具结果维度:反而 concat > window_summary(反直觉,且更要紧)

tool-medium 紧预算下,concat(头截断)8k ctx .83 / 4k .67;window_summary(对工具结果做 query 盲摘要)8k ctx .50 / 4k .17——明显更差。

原因:针是页面里一个具体事实(版本号 / 函数名 / 数字)。query 盲的摘要不知道哪句重要,把它当噪音压掉了;而 concat 的头截断只要预算够到针的位置(我们故意把针埋在中段),就原样保住。对"大工具结果里的具体针",盲压缩比笨截断还糟。

5. 推论(注意:不是结论):盲压缩到头了,指向待验证的 query 感知检索

先说清楚边界:本轮只跑了 concat 和 window_summary,RAG 还没实现、没测过。所以下面分两层——测到的和推断的,别混。

测到的(有数据):① 历史维度,window_summary > concat(摘要保留 vs 截断丢轮);② 工具结果维度,concat > window_summary(头截断保住中段针 vs query 盲摘要把具体针压没)。两条合起来:我们试过的两种 query 盲压缩,在不同维度各有失手——对"大工具结果里的具体针",两种盲压缩都救不了。

推断的(假设,待 Phase 2 验证):既然盲压缩(不看问题)在工具结果上不行,一个看问题的方法(按相关度挑 chunk)原理上应该能保住针。RAG 就是这样的方法。但这只是把"为什么想试 RAG"从随口一说升级成"有数据支撑的假设"——RAG 到底行不行、是不是真的 > window_summary,得等 Phase 2 真跑出数才算数。设计阶段那条"RAG > window_summary > concat"始终是未验证假设,本轮一个 RAG 数据点都没有。

一句话(校准过的):历史可以靠盲摘要救;工具结果里的具体针,两种盲压缩都救不了。是不是 query 感知的检索就能救——这是 Phase 2 要回答的问题,本轮没测 RAG,不下结论。

6. 工程旁注:长批处理要"单点失败不拖垮整批"

这个 sweep 第一次跑,20 个 run 丢了 4 个,耗了两小时还没结果。根因:上游 judge(/debug/regenerate → kimi)偶发 500,而 runner 里一个裸的 raise_for_status() 没人接——一次 judge 失败就把整轮(已经算完的、慢的摘要活)crash 掉,且不写结果文件。最慢的 window_summary·long(每探针一次摘要 + 多次裁判调用)三个紧预算 run 全死在这,白跑一个多小时。

修复:judge 调用重试 3 次 + 退避,失败抛 JudgeError 被单探针捕获(只让这一题判为 judge_error),整轮照常完成并落盘;/debug/regenerate 把上游传输错误转成干净的 502(而非 500 ASGI traceback)。重跑后 0 个 judge_error。教训:长批处理里每一步外部调用都要能单点失败而不拖垮整批,且中间产物要尽早落盘。生成 / 校验 / 跑批脚本一律落盘(eval/sweep_budget.sh 等)。

7. 收获清单

  • 要测"被迫取舍"这个 regime,把预算做成可调旋钮——但前提是策略真的 budget-aware,光改显示常数没用。
  • 预算做成横切 eval 参数扫现有数据集,比造新 tier 划算;默认值要等于改造前行为以免破坏基线。
  • 压缩对不对,可能取决于它知不知道"当前问题"。实测:历史可被盲摘要救;工具结果里的具体针,两种盲压缩都不可靠。是否要靠 query 感知检索(RAG)来救——是假设,留待 Phase 2 真跑后才能下结论。
  • 幻觉只有在紧预算逼出丢信息时才有信号——评测要主动制造这个压力,而不是等它自然发生。
  • 长批处理:每步外部调用单点容错 + 尽早落盘,否则一次上游抽风吃掉几小时。
